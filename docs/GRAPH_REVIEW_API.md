# Экспериментальная проверка графа через API

При загрузке в демо по умолчанию включено применение сохранённых исправлений.
В API поле `use_saved_review` запроса `POST /api/recognize` по умолчанию равно
`true`, включая запросы прежних клиентов, которые отправляют только файл.
Если SHA-256 совпадает с профилем в `focus_plan/recognition-profile.json`,
сервис заново запускает сегментацию V2 с очисткой светлой заливки и строит
граф с сохранёнными масштабом, исключениями, ответами о проёмах и проверкой
линий мебели. Выполненная сборка возвращает `pipeline=graph-review`,
`saved_review=true` и собственную ссылку на скачивание. В задании
`parent_job_id` сохраняются исходник, сегментация, классификация и ID
итогового графа. Качество проверяется на готовом графовом проекте.
Явно переданные непустые ответы `decisions` имеют приоритет.

Для нового изображения или запроса с `use_saved_review=false` работают выбранные
параметры распознавания. После него можно отдельно построить граф, указать
масштаб и выделить исключаемые области. Для старых заданий промежуточные
файлы могут быть недоступны.

Форма загрузки отправляет файл без переключателей режима. При отсутствии
профиля и явных параметров сервер анализирует уменьшенное изображение.
Для контрастного нейтрального плана с одной структурной областью, без
необходимости обрезки, он пробует V1. Этот результат принимается, если
экспорт разрешён, оценка качества равна `good` и контур каждой комнаты
занимает не менее 95 % своего ограничивающего прямоугольника.
В остальных случаях запускается V2. Повторная попытка получает отдельный ID.
Очистка светлых заливок применяется в V2 по цвету фона и наличию тёмных линий.
Если на светлом нейтральном листе обычная обработка не находит стен,
V2 пробует усилить контраст. Для применения нужны различимые штрихи двух
направлений и однозначная область чертежа. Такой проход записывается в
`preprocess.json` как `diagnostics.normalization=faint_scan_contrast`.
Поля `pipeline`, `pipeline_selection` и `light_fill_applied` показывают
выбранный режим и применение очистки для обычного распознавания.
При уточнении спорных объектов форма повторяет параметры выбранного режима.
В API `pipeline_v2=true` явно выбирает V2, `light_fill_cleanup=false` отключает очистку. Для запуска V1 передайте
`pipeline_v2=false`, а для файла с сохранённым профилем также
`use_saved_review=false`. Запрос V1 с явным `light_fill_cleanup=true`
возвращает HTTP 400.

```http
POST /api/jobs/{job_id}/graph-review
Content-Type: multipart/form-data

scale=3.9145
```

`scale` — приблизительное количество сантиметров на пиксель, положительное
конечное число; по умолчанию 1. Масштаб влияет и на построение графа, и на
размеры результата. Для focus-плана значение 3.9145 получено по размерной
линии 23,8 м и проверено по линии 8 м. Необязательное поле `scope` содержит JSON с
исключаемыми областями в координатах исходного растра:

```json
{"exclude_polygons": [[[10, 10], [80, 10], [80, 60], [10, 60]]]}
```

Области задаются только при построении нового графа. Поддерживается не более
32 корректных полигонов по 3–64 вершины внутри изображения; интерфейс создаёт
прямоугольники. Выделение удаляет геометрию в выбранной области, в том числе
части стен на границе. Его нужно проверять по исходному плану.

Ответ содержит новый `job_id`, `quality`, `review_questions`, `image_sha256`,
`scale_cm_per_px`, ссылку на изображение с вопросами и, если проверка качества
разрешила экспорт, ссылку `download_url`. Статус `review` требует проверки:
успешная структурная валидация не подтверждает точность распознавания или
совместимость с целевым приложением. При отсутствии замкнутых помещений
экспорт блокируется. Имя изображения в ответе и порядок вопросов соответствуют
друг другу; неподтверждённые объекты не изменяются.

Наружное окно может получить вопрос `possible_door_leaf_near_window`, если
рядом найдено возможное дверное полотно. Синяя линия на изображении вопросов
показывает только диагностический кандидат: похожие линии встречаются у мебели
и размерных обозначений. Тип меняется только по явному ответу; до ответа в
quality есть предупреждение `graph_possible_door_leaf`. Детектор неполон и не
гарантирует нахождение всех ошибочно классифицированных проёмов.
Когда распознанная линия обрывается рядом с косяком, она также может быть
показана для проверки; `leaf_method` позволяет отличить такую слабую подсказку.
При автоматической типизации графа для исходного класса модели door
проверяется также полотно у наружной грани косяка. Для этого нужны замкнутый
контур физических стен, согласующиеся измерения обоих косяков и направленная
наружу диагональ со свободным концом. В отчёте привязок дверей этот случай
отмечен как `outward_leaf_at_exterior_jamb`. Ширина выреза сохраняется.
Если вблизи конца линии найдены поперечные штрихи, интерфейс отдельно сообщает,
что это может быть мебель или разметка; сам по себе этот признак не доказывает
ни дверь, ни ошибку и не подавляет вопрос автоматически.

Внутренняя дверь с двумя видимыми полотнами может образовать в графе две
короткие тупиковые ветви у косяков. Этап `paired_branch_doors` сверяет каждую
ветвь с растром, проверяет свободный проём и разделение помещения. При
восстановлении в отчёте у двери указывается `source: paired_raster_leaf_branches`;
в `evidence` сохраняются координаты удалённых ветвей, а в
`type_review.evidence.leaves` — штрихи полотен.

Для внутреннего разрыва с линией неустановленного типа этап
`interior_gap_doors` сопоставляет просвет по стенам модели с косяками
на исходном растре. Чтобы добавить дверь, он проверяет диагональ от края
косяка, свободный конец полотна, отсутствие привязки к соседнему проёму
и разделение одного помещения на два. Восстановленная дверь получает
`source: interior_jamb_face_leaf`. Координаты полотна и измерения проёма
остаются в графе, причины отказа можно посмотреть в `graph_stages.json`.

Для допущенного к экспорту проекта `images.graph_export` показывает фактические
оси стен и вырезы JSON поверх исходника: жёлтым стены, зелёным двери, голубым
окна, фиолетовым открытые проёмы. Номера принадлежат отдельным типам объектов,
а не списку вопросов. Для заблокированного проекта эта картинка не выдаётся.

Для детальной проверки можно создать листы отдельных проёмов:

```bash
python scripts/review_export_contacts.py plan.png project.json graph_report.json --ground-truth partial_gt.json --output-dir review_contacts
```

Слева в каждой паре показан исходный фрагмент, справа — фактический вырез JSON.
При переданной GT отбираются элементы вне покрытых регионов; GT не участвует в
распознавании. Без GT выводятся все двери, окна и открытые проёмы. Для полной
геометрической разметки без регионов соответствующая категория считается
покрытой полностью. Результаты являются материалом для проверки, а не оценкой
правильности. Выходной каталог должен отсутствовать или быть пустым.

В отчёте `topology_gaps_omitted` перечислены виртуальные отрезки исходного
графа. Чтобы измерить их перекрытие с экспортом в плане, передайте отчёт
той же сборки в аудит вырезов. Поле `topology_gap_coverage` показывает
длину каждого отрезка внутри стены, внутри выреза и вне стен в пикселях
исходного изображения.

```bash
python scripts/audit_project_opening_holes.py project.json --graph-report graph_report.json --output hole-audit.json
```

Для уточнения отправьте поле `decisions` в новом запросе к полученному
графовому job_id. При повторной обработке того же изображения сохранённые
ответы также можно передать при первом построении графа, вместе с исходными
`scale` и `scope`. Сервис заново находит вопросы на построенном графе и
проверяет каждый ответ. Формат поля:

```json
{
  "version": 1,
  "image_sha256": "значение из ответа",
  "answers": [
    {"id": "идентификатор вопроса из ответа", "choice": "door"}
  ]
}
```

`choice` выбирается только из `choices` конкретного вопроса. Для открытого
проёма применяется шаблон целевого приложения с высотой 180 см; эта высота
не распознана с изображения и требует проверки. Пустой ответ или `undecided`
оставляют объект без решения. Устаревшие или неподдерживаемые ответы
возвращают HTTP 409. При несовпадении SHA-256 изображения API возвращает
HTTP 400. Если хотя бы один ответ отклонён, проект с частично применёнными
ответами не выдаётся. Каждый запрос создаёт отдельное задание; исходные граф и
результат не перезаписываются. При повторной проверке сохраняется масштаб
родительского графа, даже если в запросе указан другой `scale`.

В CLI тому же полю соответствует `scripts/graph_service.py --answers FILE`.
Например, в `focus_plan/opening-answers.json` сохранены ответы о двери
гардеробной, двух открытых проёмах у камина и южной перегородке холла.
Файл передаётся явно.

В CLI параметр `--furniture-review FILE` применяет визуальную проверку
коротких ветвей после ответов о проёмах. Файл
`focus_plan/furniture-review.json` хранит координаты девяти проверенных
ветвей и хеш PNG. Для записей с `expected_path` требуется точное совпадение
всех вершин от указанного конца ветви. Удалённые рёбра сохраняются
в `graph.json` в списке `diagnostics.reviewed_furniture_removals`.

Вопрос `door_between_parallel_lined_panels` появляется, когда на растре
видны косяки и полотно двери, а параллельные линии по обе стороны доходят
до существующих стен. На изображении вопросов зелёным отмечен измеренный
вырез, синим — полотно, пурпурным — боковые участки. Ответ
`solid_wall_with_door` добавляет перегородку и привязанную дверь с сохранением
измерений в отчёте. При выборе `undecided` вопрос остаётся открытым.

Файлы графа, отчёта и вопросов сохраняются в директории соответствующего
задания. Графовый режим остаётся экспериментальным: результат и масштаб
следует проверять вручную.
