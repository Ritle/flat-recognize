# Уточнение спорных проёмов пользователем

Диагностика привязки сохраняет связь `opening_id` исходного контура с UUID экспортированного элемента. Поэтому проёмы, выходящие за конец стены (`opening_exceeds_segment`), также попадают в список вопросов. Это повод проверить и тип проёма, и геометрию стены: выбор «дверь» или «окно» сам по себе не устраняет ошибку привязки, и quality gate продолжает блокировать некорректный экспорт.

Пересекающиеся параллельные окна-кандидаты с неполным подтверждением косяков получают вопрос `parallel_window_ambiguous`. Это диагностический признак возможного повторного распознавания линий мебели или оконной рамы: он не удаляет кандидаты, не меняет стены и не разрешает экспорт. Пары с двумя подтверждёнными косяками не помечаются по одному лишь пересечению.

Автоматическая привязка к другой стене допускается только тогда, когда ровно один близкий сегмент совпадает с направлением проёма и вмещает его экспортную ширину. Если подходящих сегментов несколько, диагностика сохраняет `selection: ambiguous` и их UUID в `alternative_wall_uuids`; текущая привязка остаётся для проверки. Выбор стены пользователем пока не реализован, поэтому интерфейс не предлагает фиктивного решения геометрической ошибки.

Полный CPU-прогон V2 на 10 примерах после этого ограничения сохранил статусы и числа чистого эталона (5 комнат / 5 дверей / 6 окон). Единственный перенос `span_aware` остался у `open-zones`; неоднозначных переносов в текущем наборе нет. Все 7 вылетов у `open-zones` и 8 у `complex-hatched` остались: близкого сегмента, вмещающего соответствующий проём, не найдено. Их автоматический перенос на далёкую стену исказил бы геометрию.

Дополнительная проверка соседних соосных сегментов показывает, почему одного правила объединения стен недостаточно. Из 15 вылетов только два потенциально помещаются на продолжении стены без прохождения через T/X-узел (`open-zones` №13, `complex-hatched` №17). При этом три проблемных окна на фасаде `complex-hatched` входят в размеченные реальные окна, хотя для них такое продолжение не найдено. Автоматическое удаление по факту вылета снизило бы полноту. Quality-диагностика теперь сообщает ширину проёма, длину выбранного сегмента и длину соосного продолжения; demo показывает эти величины в вопросе. Продолжение стены — диагностическая гипотеза, а не разрешение экспорта или подтверждение класса.

Demo возвращает `review_questions` вместе с результатом распознавания. Сейчас
вопросы создаются для дверей и окон с `requires_review`, а также для проёмов,
которые финальная проверка обнаружила далеко от стены или привязанными к
поперечной стене. Вопрос содержит исходный тип, координаты и прямоугольник на
изображении, причины сомнения и три допустимых варианта: `door`, `window`,
`ignore` («не проём»). Отсутствие вопросов не означает, что весь план распознан
верно: качество комнат и стен по-прежнему оценивается отдельно.

Если модель пометила контур как возможную дверь и на изображении найдены
полотно и дуга, но стена подтверждает только один косяк, контур остаётся
окном-кандидатом с причиной `door_arc_missing_jamb` и вопросом пользователю.
Автоматически считать его дверью нельзя: линии мебели способны дать такой же
признак. Выбор пользователя пересчитывает комнаты, но не снимает ошибок
геометрии и не повышает итоговый статус выше `review`.

После выбора demo повторно отправляет исходное изображение и JSON с решениями:

```json
{
  "version": 1,
  "image_sha256": "<SHA-256 исходного файла>",
  "answers": [
    {"opening_id": 8, "fingerprint": "<отпечаток контура>", "choice": "ignore"}
  ]
}
```

CLI принимает такой файл через `--review-decisions`. Хеш изображения и
отпечаток каждого контура проверяются до применения решения. Для V1 выбор
применяется после классификации, для V2 — после восстановления и фильтрации
проёмов; затем комнаты пересчитываются по изменённой классификации. Проект
строится заново, а финальный quality gate запускается без послаблений.
Ручное решение само по себе оставляет статус не выше `review`: проверка
структуры не может доказать, что выбранный пользователем тип соответствует
исходному изображению.
Если контур изменился после нового запуска модели, demo вернёт `409` и
попросит выбрать вариант заново.
Диагностические `review_decisions.json`, `classified.json`, `rooms.json` и
изображения сохраняются в каталоге job. Структура `project.json` не меняется.

Пока поддерживаются только решения о типе существующего проёма. Указание новой
стены, ручное разделение или объединение комнат потребуют отдельного формата
геометрических правок и проверки топологии до экспорта. Система не должна
предлагать для них вариант, который фактически не умеет применить.
